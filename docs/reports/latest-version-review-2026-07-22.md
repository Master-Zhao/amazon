# 《Amazon 项目最新版更新内容与不足分析报告》

> 面向普通项目成员、管理人员和非技术读者｜分析日期：2026-07-22

## 1. 执行摘要

本报告比较了 Amazon Ads Agent 仓库的三个远程分支。经刷新远程数据并核对每个分支最后一次提交时间，当前最新版是 `feature/multi-provider-langgraph-security-audit`，主要旧版本是 `agent-poc-import`。最新版直接建立在旧版之上；`main` 则属于独立的资料与汇报历史，不应被理解为软件版本的上一代或下一代。

**一句话结论：最新版已经从“单一调用方式的离线功能验证”发展为“支持多种模型服务、可视化流程编排、自动安全检查和静态演示页面的更完整技术 PoC”，但它还不是可以直接发布的产品。**

最新版最明显的三项进步是：

1. 模型服务选择更灵活：保留 OpenAI-compatible 调用方式，并增加华为云 ModelArts MaaS 适配和自动路由框架。
2. 处理流程更容易扩展：增加 LangGraph 工作流，把原来集中在循环代码中的步骤拆成可观察、可控制的流程图式结构。
3. 质量与展示手段更丰富：增加安全审计框架、相关测试、两份长篇技术文档和静态 Web Demo。

最新版最严重的三项不足是：

1. **【高】安装清单缺少 LangGraph。** 新代码已经直接使用该组件，但 `pyproject.toml` 没有声明它。在全新环境按项目说明安装后，测试会在收集阶段直接中断。
2. **【高】README、CI 与实际代码不一致。** README 仍声称未接入 LangGraph、没有前端、测试为 565 项，也没有说明 MaaS 和安全审计；这会让使用者和验收人员得出错误结论。
3. **【高】模型服务路由和网络边界不够严格。** 当前通过“网址中是否包含某段域名文字”识别 MaaS，会把相似恶意域名误判为可信服务；HTTPS 的私网地址、重定向和 DNS 解析也缺少充分限制。

**发布判断：当前版本适合继续开发和内部演示，不建议直接合并为正式发布版本，更不适合生产发布。** 在补齐依赖、修正文档与 CI、封住路由和网络边界、修复安全审计误报并建立两套工作流的自动一致性测试后，才适合进入合并评审。

## 5. 模型服务支持方面的更新

### 5.1 以前是什么情况

旧版已经能够使用离线 Stub/Fake 完成测试，也预留了 OpenAI-compatible 接口。这里的“OpenAI-compatible”并不代表只能使用 OpenAI，而是指许多厂商都采用的一种相似 HTTP 请求格式。旧版的优势是结构简单、离线可复现；不足是面向不同云厂商时需要较多定制。

### 5.2 现在变成了什么

最新版增加了华为云 ModelArts MaaS 的请求适配、响应转换和路由选择。MaaS 可以通俗理解为“由云平台托管的大模型调用服务”。项目还抽取了公共 HTTP Transport，把超时、请求预算、状态码处理等共性逻辑放到统一基类中。

### 5.3 带来的价值

这意味着项目开始从“只验证一种模型调用方式”走向“业务流程不变、模型服务可以替换”。以后接入新的兼容厂商时，理论上只需增加适配层，不必重写完整的广告建议流程。对管理人员而言，这减少了被单一模型供应商锁定的风险。

### 5.4 当前完成度

该能力属于**部分完成**。代码结构和离线测试已经存在，但本次没有真实厂商凭据，也没有执行真实网络调用，因此不能确认账号认证、配额、时延、错误响应兼容性和真实模型质量。自动路由和 Provider 命名还存在明显风险，详见第 10 章。

## 6. 工作流方面的更新

### 6.1 LangGraph 是什么

LangGraph 可以理解为“把程序处理步骤画成一张可以执行的流程图”。旧版把证据检查、候选方案生成、模型推理、输出校验、自动修订、人工介入和审批前停点串在一套循环逻辑中；最新版新增了图式实现，每个步骤成为一个节点，节点之间按结果决定下一步走向。

### 6.2 新旧工作流的关系

最新版没有删除旧工作流，而是同时保留两套实现：

- 旧工作流仍是公开 CLI 和包入口实际调用的主路径；
- LangGraph 是新的替代实现，当前没有公开 CLI 开关；
- 两套实现共用了一部分输入构建和旧格式输出函数，但仍有大量相似业务逻辑分别维护。

### 6.3 带来的价值

图式工作流更适合后续增加人工确认、异常分支、审计节点和可视化监控。它让“系统为什么停在人工介入”“一次修订后走到哪里”更容易解释，也为正式的人机协同流程提供了结构基础。

### 6.4 是否已经可以稳定替代旧工作流

目前还不能这样判断。本次临时探针对九个关键场景分别运行两套工作流，包括高 ACoS、数据不足、无需调整、非法输出后修订、重复非法输出转人工、Transport 失败、Schema 失败、运行时校验失败和审批前停点。规范化时间戳和随机事件 ID 后，两套结果在最终状态、建议值、重试次数、人工介入包、审计事件类型和生产写入标记上均一致。

这是积极证据，但仓库内现有测试是两套近似镜像测试，并没有参数化地同时调用两套实现后直接比较。未来任何一侧单独修改，都可能发生“一套修好了、另一套忘记改”的逻辑漂移。

## 7. 安全与合规方面的更新

### 7.1 新增了什么

最新版新增了安全审计命令、规则清单、文件扫描器、边界检查、配置检查、Prompt 检查和 JSON/Markdown 报告生成器。规则目标涉及凭据、生产写入、配置、HTTPS、浮点数使用、模块边界和双重确认等方面。

这是一项有价值的方向：过去主要靠开发者记住安全约束，现在开始尝试把约束变成每次都能运行的自动检查。

### 7.2 实际运行结果

使用正确入口 `python -m amazon_ads_agent.security_audit --project-path .` 运行后，报告声称检查 44 条规则：35 条合规、9 条不合规，其中 3 条 critical、5 条 high、1 条 medium，命令退出码为 1。

这些数字不能直接当作项目真实风险数量。代码检查发现，多条告警来自审计模块扫描自己的规则文字、正则表达式和实现代码。例如“禁止 Production Adapter”的规则会命中它自己的规则定义；硬编码密钥模式会命中规则中用于说明的 `AKIA` 示例。这说明框架已经能运行，但结果准确性还不足以作为合并门禁。

### 7.3 自动执行程度

审计 CLI 会执行固定的四类 Checker，但 `RuleRegistry` 并没有真正决定哪些规则执行。实测传入空 Registry，仍然得到 44 条结果。`.env.example` 是否存在虽然被计算，却没有参与最终合规判断；“双重确认”虽然计算了 CLI Flag 条件，返回结果时却只看环境变量字符串是否存在。部分文件读取或解析失败会被静默忽略。

因此，安全审计的当前完成度应标记为**仅有框架**：它展示了未来方向，但必须先修复误报、漏报和执行模型，才能用于正式结论。

## 9. 架构和维护性方面的更新

### 9.1 有利变化

新版把 HTTP 共性逻辑抽到 `BaseHTTPTransport`，把请求/响应类型抽到 `_http_types.py`，并把两套工作流共用的输入构建和旧格式输出抽到 `workflow_shared.py`。这些改动使模块职责更清楚，减少新 Provider 重复编写基础网络逻辑的成本。

### 9.2 新增维护成本

架构扩展也带来了新的复杂度：

- 同时维护旧工作流与 LangGraph 工作流；
- 自动识别协议、厂商、模型和运行模式时概念混杂；
- HTTP 基类成为多个 Provider 的共享核心，一处错误会影响全部服务；
- 安全审计模块自身拥有大量正则和扫描逻辑，也需要独立测试和维护。

这意味着项目已经从“小型 PoC 脚本”进入“需要明确架构治理”的阶段。后续不能只继续增加功能，还要建立单一事实来源、兼容策略和回归门禁。

## 10. 最新版当前存在的不足

| 优先级 | 问题 | 通俗说明 | 可能影响 | 改进建议 |
| --- | --- | --- | --- | --- |
| 高 | LangGraph 依赖未声明 | 新车装了一个关键部件，但交付清单里没有它 | 新用户安装后导入失败，CI 无法完成测试 | 把 LangGraph 明确列为必需依赖，或做成清晰的可选 extra，并让导入延迟、错误可读 |
| 高 | README 与代码、测试和 CI 不一致 | 使用说明仍描述旧版本 | 项目成员、管理者和验收人员会作出错误判断 | 同步功能清单、目录、安装命令、测试数字、Demo 和 PoC 边界；CI 必须执行相同命令 |
| 高 | Provider 路由过于宽松 | 仅凭网址里包含一段文字判断服务商 | 恶意或错误地址可能被当成可信 MaaS，错误也会归因给错误厂商 | 使用精确主机名或有边界的允许子域；加入协议、端口、DNS、私网和重定向检查 |
| 高 | Provider 身份含义混杂 | Stub、协议类型、真实厂商和模型名称挤在少数字段中 | 日志、错误、统计和审计身份不可信 | 分离 `execution_mode`、`protocol_type`、`vendor_id`、`model_id`、`endpoint_id` |
| 高 | 安全审计误报、漏报且 Registry 无效 | 检查器会“检查到自己”，部分声称的条件没有真正参与判断 | 可能把安全项目误判为危险，也可能让真实问题通过 | 让 Registry 驱动执行；使用 AST/配置解析；排除规则自身和 fixture；读取失败要显式报告 |
| 中 | 两套工作流可能逐渐不一致 | 同一业务维护两套流程 | 修复一边后另一边可能遗漏，结果逐渐分叉 | 建立参数化 parity 测试，并明确主实现；CLI 提供选择或迁移计划 |
| 中 | HTTP 重试和诊断能力不足 | 网络忙或服务端限流时会立即重复请求，错误信息还会丢失 | 放大限流、恢复变慢、难以定位厂商问题 | 增加指数退避、抖动、Retry-After、总时限；保留脱敏响应摘要和服务端 Request ID |
| 中 | 请求预算不是线程安全的 | 多个请求同时执行时，计数可能不准确 | 并发环境可能超预算或错误拒绝请求 | 使用锁或原子计数，并增加并发测试 |
| 中 | Demo 容易被误认为审批系统 | 页面有“验收通过”字样，但按钮只改变本地状态 | 截图或演示脱离上下文后可能误导 | 永久标注“静态合成数据/非审批系统”，改成只读加载脱敏本地结果 |
| 中 | 缺少生产化能力 | 没有 Amazon Ads API、认证、正式审批、生产写入、监控、部署和回滚闭环 | 无法承担真实业务和生产责任 | 另立生产化项目阶段，逐项设计接口、安全、可观测性和发布治理 |
| 低 | 安全审计 CLI 使用方式不够直观 | 位置参数会报错，正确命令需要 `--project-path` | 增加学习成本和误操作 | 提供 console script、`--help` 示例并同步 README |

## 11. 高优先级改进事项

### 11.1 先恢复“按说明即可安装和测试”

受影响的人：所有首次安装的开发者、CI 和验收人员。

如果不改：任何新增功能讨论都会被“干净环境无法跑完测试”这一事实否定。

建议：明确 LangGraph 是正式交付能力还是实验能力。若是正式能力，加入必需依赖并锁定兼容范围；若是实验能力，加入 `langgraph` extra，延迟导入，并在 CLI 中给出清晰安装提示。验收标准是全新 Python 3.11/3.12 环境只执行 README 命令即可完成导入和全量 pytest。

### 11.2 让 README、CI 和当前代码说同一件事

受影响的人：项目成员、管理者、评委、交付和运维人员。

如果不改：同一个仓库会产生互相冲突的事实，导致错误排期、错误验收和错误发布决定。

建议：README 自动引用或由 CI 验证当前测试数字；明确 Fake 评估不是模型质量；列出 MaaS、LangGraph、安全审计和静态 Demo；明确没有 Amazon Ads API、生产写入和正式 Approval Service。

### 11.3 封住模型路由与网络边界

受影响的人：部署人员、网络环境和凭据持有人。

如果不改：错误或恶意 URL 可能被识别成可信厂商，重定向或 DNS 变化可能把请求引向私网或元数据地址。

建议：显式配置协议和厂商优先，自动识别只作兼容；使用主机精确匹配或边界清晰的子域匹配；限制 HTTPS、端口、DNS 解析后的私有/环回/链路本地地址，并在每次重定向后重新校验最终 URL。

### 11.4 让安全审计先证明自己可信

受影响的人：安全评审、合并审批和管理者。

如果不改：项目可能因为误报告警被阻塞，也可能因为漏报产生虚假安全感。

建议：Registry 成为唯一执行清单；源代码规则优先使用 AST，配置规则使用 TOML/YAML/ignore 解析，凭据规则排除自身定义和测试 fixture；任何文件读取或解析失败都形成显式 finding。完成前不应把当前 44 条结果作为发布门禁。

## 12. 中低优先级改进事项

1. **【中】固化双工作流一致性。** 把本次九场景临时探针变成仓库测试，一次输入同时运行两套流程并比较状态、建议、重试、人工介入包、审计序列和生产写入标记。
2. **【中】提高 HTTP 可靠性。** 增加线程安全预算、指数退避、抖动、`Retry-After`、总时限、响应体脱敏摘要和服务端 Request ID 来源字段。
3. **【中】重构 Provider 身份。** 让“离线/在线模式”“协议”“厂商”“模型”“端点”分别有字段，并提供旧字段的兼容迁移期。
4. **【中】重新定位 Demo。** 改为读取用户主动选择的脱敏本地 JSON，只读展示真实运行结果；永久显示“非审批系统”水印，并增加前端与可访问性测试。
5. **【中】制定生产化路线。** Amazon Ads API、认证授权、正式审批、持久化审计、监控告警、部署、回滚和灾备应作为独立里程碑，不应继续隐含在 PoC 中。
6. **【低】改善命令体验。** 提供安全审计 console script、一次运行示例和清晰退出码说明。

## 14. 当前版本是否适合合并或发布

| 使用场景 | 建议 | 理由 |
| --- | --- | --- |
| 继续开发 | 适合 | 新架构和测试可作为后续开发基础 |
| 内部演示 | 有条件适合 | 必须明确 Demo 是静态页面、评估是 Fake、没有生产写入 |
| 合并到主开发分支 | 暂不建议 | 依赖、README/CI、网络边界和安全审计门禁尚未修复 |
| 小范围试运行 | 不建议 | 尚未验证真实厂商调用、认证、配额、监控和回滚 |
| 正式生产发布 | 不建议 | 没有 Amazon Ads API、正式审批服务、生产写入和生产运维闭环 |

合并前最低门槛是：依赖与 CI 恢复、README 同步、Provider 路由负向测试通过、安全审计不再自扫描误报、九场景 parity 成为仓库自动化测试。

## 15. 结论

最新版最大的进步，是把一个以离线流程验证为主的 PoC 扩展成了更完整的技术平台雏形：模型服务可以适配不同厂商，处理步骤可以用 LangGraph 表达，安全规则开始自动化，测试、规范和演示材料也明显增加。相比旧版，项目在可扩展性、可观察性和交付表达方面都更成熟。

但是，“功能更多”不等于“已经可交付”。当前最严重的三个不足是：LangGraph 依赖没有进入安装清单；README、CI 和代码事实互相冲突；Provider 路由与网络边界存在可复现的误判和 SSRF 风险。此外，安全审计自身会产生误报，两套工作流也缺少仓库内直接一致性门禁。

**明确判断：当前版本最适合继续开发和受控的内部演示，不适合直接合并为发布版本，不适合小范围真实业务试运行，更不适合正式生产发布。**

下一步最应该先做三件事：

1. 补齐 LangGraph 依赖并让干净环境、CI 和 README 安装命令完整通过；
2. 同步 README 与实际能力，明确 Fake 评估、静态 Demo 和 PoC/生产边界；
3. 修复 Provider 路由、SSRF 边界和安全审计准确性，并把九场景工作流 parity 加入自动化测试。
