# 亚马逊广告智能体项目场景与痛点提炼

> 提炼依据：`docs/agent/amazon-ads-agent-loop-engineering-spec-v0.2.md`（2026-07-16，待评审）

## 一、项目定位

本项目面向亚马逊广告投放与运营团队，建设一个“智能分析、确定性计算、人工审批、受控执行、结果对账、全程审计”的广告优化智能体闭环。系统利用智能体降低多层级广告数据分析、方案解释和组织成本，但不让大模型直接决定关键数值或绕过人工授权；预算、竞价、平台边界、审批和生产写入均由确定性规则及服务端守卫控制。

## 二、概括性场景

广告投手需要持续查看 Campaign、Ad Group、Product Ad、Keyword 和 Target 等对象的曝光、点击、消耗、订单与销售数据，并根据转化率、ACoS、ROAS、预算利用率等指标判断是否调整竞价或预算。系统读取授权范围内的数据快照，识别值得处理的对象，生成有数据依据且位于安全边界内的候选方案，并给出可读解释。方案通过结构校验和执行预检后被冻结，交由有权限的人员审批；只有审批、对象当前值、对象版本、锁和幂等校验全部通过，系统才允许受控执行。执行结束后逐项记录结果；若出现冲突、部分成功或状态未知，则只读对账并转人工处理，不自动重放、回滚或补写。

典型业务场景包括：

1. **高点击、低转化**：识别点击达到阈值但转化表现偏低的 Keyword 或 Target，在样本和规则充分时生成确定性的降价候选。
2. **ACoS 超出目标**：当实际 ACoS 高于目标且样本量满足要求时，给出竞价降低候选；数据不足时不贸然调整。
3. **预算可能受限**：结合预算利用率、投放周期进度、订单量和 ROAS 判断是否需要提高预算，并确保候选不超过策略、账户和平台上限。
4. **证据不足**：分析周期、样本量、关键阈值或平台边界不完整时，只输出风险提示，不生成可执行变更。
5. **当前无需调整**：数据充分但没有规则被触发，或合法候选集合为空时，直接给出“无需变更”结论，避免无意义操作。
6. **异常与冲突处理**：审批失效、对象值或版本变化、权限/API 异常、部分成功、执行状态未知等情况均停止自动执行，进入对账或人工介入流程。

## 三、痛点说明

### 1. 数据层级多，人工分析成本高

亚马逊广告包含多个对象层级和大量指标，运营人员需要反复汇总、比较并定位异常对象。单纯依赖人工容易耗时，也难以保证每次分析都覆盖相同范围和采用相同口径。

### 2. 判断口径依赖个人经验，结果不稳定

不同广告投手对样本量、目标指标、风险偏好和调整幅度的理解可能不同，同一组数据可能得到不同结论。若关键阈值和计算规则没有版本化，方案难以复现，也难以解释“为什么这样调”。

### 3. 原生工具难以形成完整、可验证的操作闭环

传统工具通常能展示数据或支持单点操作，但难以自动串联“候选计算—解释—校验—审批—受控执行—对账—审计”。分析依据、审批内容与最终写入结果分散后，出现问题时难以还原全过程。

### 4. 大模型输出存在漂移，不能直接作为生产写入依据

大模型适合做解释、分类和方案组织，但可能产生不稳定文本、越界数值或不存在的对象。如果让模型自由决定竞价、预算或平台上下限，会带来不可预测的资金和投放风险。

### 5. 生产执行涉及权限、审批和数据时效风险

从方案生成到实际执行之间，对象值、版本、权限或规则可能已经变化。若审批身份来自客户端、审批过期后仍可使用，或方案冻结后还能被修改，就可能造成未经授权或与审批内容不一致的写入。

### 6. 并发、重复提交和执行异常可能破坏账户一致性

多个任务可能同时修改同一对象，网络超时也可能让执行结果处于未知状态。若采用最后写入覆盖、自动重试或重复使用审批，可能造成重复扣量、覆盖他人调整或账户状态不一致。

### 7. 数据或配置不完整时，系统容易给出“看似合理”的错误建议

目标 CVR、样本阈值、预算周期、平台最小/最大值、货币精度和步长等配置缺失时，任何默认猜测都可能让方案越界。因此，系统必须在证据不足时停止生成可审批方案，而不是由模型补全未知信息。

### 8. PoC 能力容易被误当成生产能力

合成数据、内存锁、API Stub 和 `dry_run` 可以验证流程，但不等于 Amazon Ads API、沙箱、部署或线上写入已经完成。如果测试能力与生产能力不明确区分，容易产生错误预期，并把简化设计带入生产环境。

## 四、核心解决思路

- **智能体负责理解与表达**：解释多指标关系、分类问题、在合法候选中排序、生成理由和风险摘要。
- **确定性模块负责关键决策**：统一计算指标、样本充分性、候选集合、Decimal 精度、调整比例、平台边界和最终摘要。
- **人工审批控制生产动作**：方案通过校验和预检后冻结，必须由认证系统确认的授权人员审批。
- **服务端守卫保证执行安全**：写入前再次校验审批、摘要、对象范围、当前值、对象版本、锁和幂等键，任一不满足即拒绝写入。
- **异常路径默认安全停止**：部分成功、状态未知或对账不一致时禁止自动重放与补偿，保留逐项结果并转人工处理。
- **审计证据贯穿全流程**：关联任务、数据快照、规则版本、方案版本、审批记录、执行结果和对账结果，使过程可查询、可复现、可追责。

## 五、预期价值

1. 降低广告数据筛选、异常定位、方案组织和说明成本，提高投手处理效率。
2. 通过统一指标、规则版本和确定性候选，减少不同人员之间的判断偏差。
3. 让每项建议都能追溯到同一数据快照和明确证据，增强方案可解释性。
4. 通过人工审批与多重写入守卫降低越权、越界、误写和重复执行风险。
5. 对“无需调整”和“证据不足”给出明确终止结论，避免为了自动化而产生无意义变更。
6. 为 PoC、内部 MVP 和后续生产化提供统一的工程基线及验收依据。

## 六、当前阶段与边界

当前最新文档是一份**待评审的 V0.2 工程规范**，定义了目标流程、协议、安全规则、测试与验收基线，但不代表相关代码、JSON Schema 独立文件、Amazon Ads API 对接、沙箱、部署、生产写入或线上验证已经完成。

现阶段 PoC 可使用合成数据、API Stub、内存锁和 `dry_run` 验证闭环；正式进入生产前，仍需确认 Amazon Ads API 权限与实体映射、平台预算/竞价边界、账户安全上限、业务阈值、审批有效期、并发条件写能力及人工补偿流程。任何生产阻断配置未确认时，系统应保持只读或拒绝执行。
